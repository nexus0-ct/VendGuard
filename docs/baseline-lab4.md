# Базова лінія VendGuard для ЛР4

Стан: поточні входи заморожено як `vg3-eed2dae477f4fd8f`, ELF SHA-256 `b6681b1a211dcd06cc175925fb4d651db004903671e63df4c761d41684c46ca0`. Після виправлення UART завершені нові вимірювання29.10.2026; числовий baseline у docs/lab3-report.md та current-eed2/final-assessment.json. Попередні S1/S2 та невдалі S3 збережено під ідентифікатором попередньої збірки в [реєстрі результатів](metrics/lab3/README.md). ЛР4 тут не реалізована. Числа host-моделі не є базовою лінією швидкодії MCU.

## Незмінні умови

STM32C031C6, HCLK/PCLK 48 МГц; HAL з ЛР2; UART 115200 8N1; MPU ±2g, 100 Гц, DLPF 44 Гц; LDR 50 Гц. Початково MPU Z=1g, X=Y=0; LDR 1 lux, PIR LOW. Фон накопичити до `calibrated=1 light_ready=1`. Ідентифікатор поточних входів збірки видає `python3 tools/source_id.py`; прошивка повертає той самий рядок командою `version`.

Збірка `make build`, тести `make test`, `make sanitize`. Використовувати власний образ `vendguard-build:lab3`; digest і точні версії зберігати у manifest. Ні гілка, ні Git HEAD без fingerprint не визначають незакомічену збірку.

## Сценарії

Команди виконуються після фактичного запуску Wokwi або на платі з окремим UART-адаптером. Скрипт не запускає симулятор і не створює даних датчиків. Для RFC2217:

```sh
python3 tools/run_lab3.py S1 --output docs/metrics/lab3/S1.uart.log
python3 tools/run_lab3.py S2 --seconds 3660 --output docs/metrics/lab3/S2.uart.log
python3 tools/run_lab3.py S3 --seconds 240 --s3-interval .75 --s3-status-count 20 --s3-handshake --s3-mode guard --output docs/metrics/lab3/S3-A.uart.log
python3 tools/run_lab3.py fault --output docs/metrics/lab3/fault.uart.log
python3 tools/run_lab3.py boundary --output docs/metrics/lab3/boundary.uart.log
```

Потрібен pyserial 3.5; порт 4136. Файли не перезаписуються. Вихідний manifest містить команди, час хоста для керування впливами, source fingerprint, HEAD, SHA-256 логу й тривалість. Час реакції брати з таймера MCU та VCD, не з прибуття рядка на хості.

Перезапуск Wokwi з повторним завантаженням HEX не є сам по собі фізичною втратою живлення з гарантованим збереженням NVM. Якщо flash не підтримана, записати фактичний результат, а сценарій power-cut залишити непідтвердженим.

## Метрики та методи

Спочатку виконати короткий S3 regression pilot: ті самі .75/20, `--seconds 30 --allow-short`. Це перевірка завершення команд, повного stats, TX-лічильників та приймання після timeout, а не підсумковий S3 або endurance.

`measure on` скидає статистики й фазу розкладу. `stats` спочатку зупиняє накопичення, потім виводить STAT/SCHED/JITTER/COUNTERS/MEM. Блок виведення статистики не включено у вимірюване вікно. Наступне `measure on` починає нове. RX/PIR/audit/TX лічильники накопичуються від старту MCU; без початкового знімка вони описують увесь запуск, включно з warmup і заповненням журналу. Не видавати їх за приріст усередині вікна.

Runner приймає timestamp лише після пробілу за всіма цифрами та вимагає повні 14 STAT, 8 SCHED, 8 JITTER, COUNTERS і MEM. Неповна відповідь або коротше за годину MCU-вікно S2 завершується помилкою. `--allow-short` залишає явну позначку development. Запас 3660 с не замінює перевірку фактичного MCU elapsed. Manifest зберігає також хеші runner і parser.

`STAT` дає n/min/avg/max у мкс. `JITTER` дає середнє зі знаком і гістограму абсолютного джитера за межами 10/100/1000 мкс. Нуль запусків не означає нульову тривалість. `task_load_permille` враховує лише роботу задач; нескінченний busy-spin головного циклу не є вільним CPU. Фізична зайнятість без WFI близька до 100%, оцінка корисної роботи має інший зміст.

`command_latency` рахується від отриманого термінатора CR/LF до початку обробки, `command_complete_latency` до повернення з передачі відповіді та VG DONE. Керівні `measure on/off` і `stats` виключені з цих двох метрик. Скидання вікна має generation guard, тому залишок старого циклу не додається до нового. `clock_read` містить 256 стартових пар читань таймера. Стек вимірюється від першого main, тому містить також максимум init; для окремих сценаріїв потрібні окремі reset.

У безкоштовному веб-Wokwi RFC2217 може бути відсутнім. Тоді ті самі команди виконуються через Serial Monitor, збережені raw UART/VCD та ручний manifest. Це окремий спосіб подання входів, його не слід видавати за виконання Python runner. Розклад рідкісних команд, кількість подій і момент запуску `measure on` треба записати фактично. Повторення в ЛР4 має використовувати саме підтверджений спосіб.

Для аналізатора зберегти оригінальний VCD перед новим запуском. Роздільність VCD не є точністю реальної плати. Зіставити MPU_TASK periods/width та STAT mechanical, PIR→CUSTOMER_RESPONSE і STAT pir_latency. ISR-мітка не включає затримку входу в ISR, GPIO включає її. Перевірити однакову кількість входів/реакцій і нуль втрат перед однозначним FIFO-зіставленням.

`bufferSize=10000000` означає 10 мільйонів переходів усіх каналів, близько 90 МБ RAM браузера, а не пам'ять C031. Для годинного S2 звірити останній timestamp VCD та лічильник заповнення з кінцем вимірюваного вікна. Не припускати, що буфер охопив усю годину. Джерело визначення буфера: [Wokwi logic analyzer](https://docs.wokwi.com/parts/wokwi-logic-analyzer).

У VS Code поточний raw-файл `docs/captures/lab3/vendguard-current.vcd` ігнорується Git. У вебі ім'я `vendguard-lab3.vcd`. Після Stop зберегти файл у каталозі власника й архівувати:

```sh
python3 tools/archive_lab3_capture.py S3-20261028-01 --notes 'Фактично виконані дії та межі запису'
```

Архіватор відмовляється перезаписувати наявний запуск і відкидає відому копію ЛР2. Manifest містить SHA-256, вихідний заголовок, очікуваний build/ELF і схему. Підтвердити справжній BOOT/VERSION за UART. Для декодування самого VCD:

```sh
python3 tools/decode_lab3_uart.py docs/captures/lab3/S3.vcd --output docs/metrics/lab3/S3-decoded
```

Текст `S3-decoded.uart_tx.txt` є похідним із переходів, його не називають оригінальним serial capture. JSON зберігає часові позначки байтів/рядків і хеш джерела.

```sh
python3 tools/analyze_lab3.py docs/metrics/lab3/S3.uart.log \
  --vcd docs/captures/lab3/S3.vcd \
  --decoded-uart docs/metrics/lab3/S3-decoded.json --output docs/metrics/lab3/S3.analysis.json
```

Decoded UART задає внутрішню межу MEASURE→METRICS із відступом 1 мс; для кількох вікон потрібен `--window-index`. `pir_during_journal` рахує лише фронти між першим RECORD-байтом і DONE stop bit. Для LDR використовують контрольовані переходи між 1 та приблизно 525 lux: спад LDR_DO позначає вхід, останнє завершення ADC перед прямою LDR-подією дає нижню кінцеву точку, перший UART-байт EVENT — верхню. Mode-induced події виключаються. Відсутній рядок за TX-помилки не доводить відсутності внутрішньої події.

Остаточні таблиці S1/S2/S3 отримані з поточних файлів. MCU min/avg/max, stack/heap, затримки й межа bursts містяться в current-eed2 та звіті. Статичні ресурси й host-перевірки зберігаються окремо в `docs/metrics/lab3/`. Фізичний power-cut/ECC лишається окремою межею симулятора.

Гіпотези для майбутньої ЛР4 наведено в `limitations.md`. Порівнювати на тому самому MCU, з тими самими входами, UART і маркерами. Окремо виміряти ціну стеків задач, планувальника, контекстних перемикань і черг. Не приписувати RTOS можливість усунути фізичний stall внутрішньої flash.

Фактичний handshake S3: порожній LF,200 мс pump,journal,15 мс,20 status,очікування DONE до2 с,200 мс pump. Ціль .75 с ±25% seed36 може подовжуватися handshake. Для повторення фактичні timestamps наведені у manifests. NACK-final використовує --fault-nack-seconds 20. Усі ці значення стосуються поточного ELF.
